# LogiOn AI 파트 중간 정리 (v1 → v2)

작성 2026-10-23 / 브랜치 `ai-improve-1022` / 모든 수치는 실제 실행에서 나온 값입니다. 돌리지 못한 것은 **미실행**으로 적었습니다.

파이프라인: 음성 → STT(SenseVoice) → **의도분류(klue/roberta-small)** → **function calling(Qwen2.5-1.5B + LoRA)** → 규칙 `resolve()` → 가상 DB → 답 문장 → TTS(VITS)

## 3. 개선 작업과 그 결과

### 3-1. 데이터·규칙 수정 (1단계)

| 한 일 | 결과 (실측) |
|---|---|
| 모든 틀의 고정 문구를 훑어 수량 표현이 있는데 정답에 qty 가 없는 것을 찾음 | 틀 1개(`{item} 박스 하나 {issue}`), 문제 표현 1개(`하나 빠졌어`) 발견 → 규칙으로 고침 |
| 제미나이 데이터의 수량 라벨도 같은 기준으로 보정 | 2건 보정 (말하지 않은 unit 을 지움) |
| "둘·다섯"처럼 단위 없이 말하는 경우를 넣고, 그때는 정답에 qty 만 쓰도록 | 재생성 후 **"수량을 말했는데 정답에 qty 가 없는 report_issue 문장 = 0건"** (고치기 전 27건) |
| 단위를 개·박스·판·봉지로 맞추는 규칙(`snap_unit`) | 답 문장에서 단위가 뒤섞이는 것 방지 |

데이터는 2,754문장 (train 1,940 / val 383 / test 431), 기능마다 약 460건으로 그대로입니다.

### 3-2. 선택지로 되묻기 (2단계)

의도분류 1등과 2등 확률 차(margin)가 기준 tau 보다 작으면 **실행하지 않고 두 후보를 말해 주며 되묻습니다.**

- 예: "남은 배송지 말씀하시는 건가요, 내릴 물건 말씀하시는 건가요?"
- 기사가 "배송지" / "물건" / "첫 번째" 처럼 답하면 이어서 처리합니다. (데모에서 확인)
- 2등이 `other` 면 선택지를 주지 않고 "다시 말씀해 주세요" 로 답합니다.
- `next_stop`·`scan`·`other` 는 확률 ≥0.9 면 LLM 을 건너뜁니다 → test 에서 **45.5%** 가 LLM 없이 처리됩니다.

**지시된 tau 선택 규칙의 한계 (실측으로 확인)**

| val tau | 되묻기 비율 | 실행 정확도 | 되묻기 포함 성공률(지시된 기준) |
|---|---|---|---|
| 0.00 | 0.0% | 0.916 | 0.916 |
| **0.05 (선택)** | 0.3% | 0.916 | 0.916 |
| 0.20 | 2.6% | 0.930 | 0.911 |
| 0.40 | 4.2% | 0.937 | 0.906 |
| 0.50 | 6.3% | **0.944** | 0.898 |

실행 정확도는 tau 가 커질수록 계속 오르는데, 지시받은 기준(되묻기 포함 성공률, 의도분류 기준)은 반대로 내려갑니다. 그래서 이 기준은 **되묻기를 가장 적게 하는 tau** 를 고르게 되고, 실제로 tau=0.05 가 뽑혀 **test 431건 중 2건(0.46%)만 되묻습니다. 즉 지금 설정에서 이 기능은 거의 발동하지 않습니다.**
지시받은 규칙을 바꾸지 않고 그대로 따랐습니다. 실행 정확도를 기준으로 고르면 tau≈0.4~0.5 가 뽑히며, 그때 되묻기 4~6%에 실행 정확도 0.937~0.944 입니다. **기준을 바꿀지는 결정이 필요합니다.**

### 3-3. 재학습과 비교 (3단계)

두 모델을 **같은 새 test 431건**으로 평가했습니다. 틀 배정은 v1 것을 그대로 써서(`data/template_split_v1.json`) v1 이 학습에서 본 틀이 새 test 에 들어가지 않게 했습니다. v1 의 train·val 문장과 겹친 새 test 문장은 **0건**이라 "clean" 열은 전체와 같습니다.

| 지표 | v1 | v2 | 차이 |
|---|---|---|---|
| 의도분류 정확도 | 0.893 | **0.907** | **+0.014** |
| 의도분류 macro F1 | 0.895 | **0.905** | **+0.010** |
| FC JSON 유효율 | 1.000 | 1.000 | 0 |
| FC fn 정확도 | 0.916 | 0.886 | −0.030 |
| FC 완전일치 | 0.896 | 0.847 | −0.049 |
| FC 값 F1 | 0.976 | 0.968 | −0.008 |
| **FC 최종동작일치** | **0.898** | **0.847** | **−0.051** |
| 전체 파이프라인(되묻기 없음) | 0.937 | 0.845 | −0.093 |
| 되묻기 비율 | 6.5% | 0.5% | −6.0%p |
| 틀리게 실행한 비율 | 0.063 | 0.151 | +0.088 |

v2 가 v1 보다 새로 맞힌 것 15건, 새로 틀린 것 37건입니다. **틀린 37건 중 25건이 아래 두 틀에서 나왔습니다.**

#### 원인 A — 1단계 라벨 수정의 예견된 부작용 (틀 `{item} 박스 하나 {issue}`, test 17건, v1 13/17 → v2 1/17)

1단계 감사에서 이 틀의 "박스 하나"에 수량 표현이 있는데 정답에 qty/unit 이 없던 것을 찾아 **qty=1, unit="박스"** 로 고쳤습니다(v2 test 숫자를 보기 전에 기록된 사실입니다). 그런데 **이 틀은 v1 의 고정 배정에서 test 로만 들어가 있습니다(train 0건 / test 17건).** 동시에 1단계에서 "하나·둘·다섯"처럼 단위 없이 말하면 정답에 qty 만 쓰는 규칙을 넣었습니다.

결과적으로 v2 는 "박스 하나"를 학습에서 한 번도 못 본 채 **"하나 → 단위 없음"** 규칙만 배워서 unit 을 빼먹습니다.

| 문장 | 정답 | v1 | v2 |
|---|---|---|---|
| 제육도시락 박스 하나 다 녹았어 | `qty:1, unit:"박스"` | `qty:1, unit:"박스"` ✅ | `qty:1` ❌ |
| 그 샌드위치 박스 하나 덜 왔어 | `qty:1, unit:"박스"` | `qty:1, unit:"박스"` ✅ | `qty:1` ❌ |

**→ 다음 반복에서 고칠 것:** `{qty}` 자리를 "박스 하나"처럼 **단위-먼저** 형태로도 렌더링해 train 에 넣습니다. 틀 목록 자체는 건드리지 않으므로 고정 배정과 공정 비교가 유지됩니다.

#### 원인 B — 설명되지 못한 일반화 손실 (틀 `물건 확인할게`, test 13건, v1 13/13 → v2 0/13)

v2 오답을 읽다가 발견한 관찰입니다(미리 예측한 것이 아닙니다). 정답은 `scan` 인데 v2 는 13건 전부 `stop_items` 라고 답합니다. 이 틀도 train 0건 / test 13건입니다. train 에서 "물건"이라는 단어가 stop_items 쪽에 많아 끌린 것으로 보이지만, **v1 도 같은 배정으로 학습했는데 맞혔으므로 원인을 확정하지 못했습니다. 미해결로 남깁니다.**

#### report_issue — 라벨 버그를 없앤 맞교환

| | v1 (v1 옛 test) | v2 (새 test) |
|---|---|---|
| report_issue 오답 | 24건 | 26건 |
| 그중 **라벨 버그** | **11건** | **0건** |
| 그중 수량·단위 생성 | 2건 | 16건 |
| 그중 본질적 모호성 | 9건 | 9건 |

1단계가 라벨 버그를 완전히 없앴고(11 → 0), 그 비용이 원인 A 의 수량·단위 쪽으로 옮겨 갔습니다. 즉 **데이터 잘못은 해결됐고, 남은 것은 학습 데이터 커버리지 문제**입니다.

#### next_stop — 잘못된 실행의 주된 경로

v2 FC 최종동작일치 0.770 (v1 과 동일), 오답 17건 전부 `기능 혼동`입니다. 더 중요한 것은 의도분류 쪽입니다.

의도분류 혼동(v2): `other` 70건 중 **24건을 `next_stop` 으로** 잘못 봅니다 ("근처 화장실 어디야", "지금 몇 시야" 등). `next_stop` 은 확률 ≥0.9 면 LLM 을 건너뛰고 바로 실행하는 기능이라, 이 오분류가 **그대로 잘못된 실행**이 됩니다. v2 의 "틀리게 실행한 비율" 15.1%가 여기서 나오고, 파이프라인 정확도가 FC 단독보다 더 많이 떨어진 이유입니다.
→ `next_stop` 을 LLM 건너뛰기 대상에서 빼거나, `other` 쪽 학습 문장을 늘리는 것이 다음 후보입니다.

## 4. 보드 변환·측정

### 4-1. 의도분류 ONNX (실행 완료)

| | 정확도 | PyTorch 와 예측 일치 | 크기 | CPU 1문장(4스레드) |
|---|---|---|---|---|
| PyTorch | 0.9072 | – | 259.8 MB | 15.1 ms |
| ONNX fp32 | 0.9072 | 1.000 | 259.9 MB | 6.5 ms |
| **ONNX int8** | 0.9118 | **0.9907** | **65.3 MB** | **2.9 ms** |

- int8 정확도가 0.5%p 높은 것은 431건 중 2건 차이로, **양자화가 더 좋아진 게 아니라 측정 오차 범위**입니다. 예측 일치율 99.07%(4건 불일치)로 보는 것이 맞습니다.
- **이 시간은 이 PC 의 CPU 값이고 보드(RK3588) 값이 아닙니다.**
- 보드용 추론 코드 `export/intent_onnx/infer.py` 는 onnxruntime + tokenizers 만 쓰고 torch 가 필요 없습니다 (동작 확인).

### 4-2. RKLLM W8A8 변환 — **미실행**

**이유: 변환 도구가 이 PC 에 없습니다.** rkllm-toolkit 은 x86 Linux 전용인데 WSL 배포판·Docker·toolkit 휠이 모두 없습니다.

toolkit 없이 되는 준비 단계는 실제로 돌려 확인했습니다 (`python export/convert_rkllm.py --prepare-only`):

| 확인한 것 | 결과 |
|---|---|
| 캘리브레이션 데이터 | 450건, `export/calibration_w8a8.json` (채팅 템플릿 적용 프롬프트 + 정답) |
| max_context | 데이터 최대 토큰 179 → 32 배수 192 → 여유 두어 **256** |
| 종료 토큰 | `<|im_end|>` = **151645** 로 정상 등록 확인 (보드 서버도 이 id 사용) |
| 보드 생성 설정 | 학습·평가와 맞추려면 **top_k=1(탐욕), repeat_penalty=1.1** |

### 4-3. 보드 평가·단계별 지연 — **미실행**

**이유: 보드 주소·SSH 정보가 주어지지 않았고, 변환된 `.rkllm` 파일도 없습니다.** `results/v2/board/` 는 비어 있습니다.
스크립트는 준비돼 있습니다: `scripts/board_eval.py` (보드 LLM 정확도 + PC 원본과 비교 + TTFT), `scripts/board_latency.py` (STT/의도분류/LLM/규칙/TTS 단계별 ms). 전자는 가짜 서버(`--selftest`)로 코드 동작까지 확인했습니다.

## 5. 지금 상태와 다음 할 일

**끝난 것**: 데이터·규칙 수정, 선택지 되묻기 구현, 두 모델 재학습과 공정 비교, 오류 원인 분석, 의도분류 ONNX 변환·검증, 보드용 스크립트 일체.

**결정이 필요한 것**
1. **tau 선택 기준** — 지금 기준은 되묻기를 사실상 끄게 만듭니다. 실행 정확도 기준으로 바꿀지 결정이 필요합니다.
2. **원인 A 수정 후 재학습** — `{qty}` 를 단위-먼저 형태로도 렌더링해 재학습하면 회귀의 큰 쪽이 풀릴 것으로 봅니다. 다만 **v2 의 test 오답을 보고 데이터 규칙을 바꾸는 것이라 test 에 맞춰 조정하는 셈**이어서, 이번에는 일부러 하지 않고 보고만 합니다.
3. **`next_stop` 의 LLM 건너뛰기** — `other` 오분류가 그대로 잘못된 실행이 되므로 재검토가 필요합니다.

**사람이 직접 해야 하는 것**
- RKLLM 변환: x86 Linux(또는 WSL2/Docker)에 rkllm-toolkit 설치 후 `python export/convert_rkllm.py --model-dir out/fc_merged --out export/model_w8a8.rkllm`
- 보드에 `.rkllm` 올리고 OpenAI 호환 서버 띄운 뒤 `scripts/board_eval.py --base-url http://<보드IP>:<포트>/v1`
- SenseVoice·VITS 모델을 보드에 두고 `scripts/board_latency.py` (실제 녹음 wav 가 있으면 `--wav-dir` 권장, 없으면 합성 음성 기준으로 기록됨)
