## 판단 기록 (질문 대신 정한 것들)

1. **v2 템플릿 분할은 v1 과 같은 틀 배정을 쓴다.** 수정한 코드로 데이터를 다시 만들면 난수 흐름이 바뀌어 "어떤 틀이 test 인지"가 달라지고, v1 이 학습에서 본 틀이 새 test 에 들어가 v1 점수가 부풀려질 수 있다. 그래서 v1 의 틀 배정을 고정(`data/template_split_v1.json`)했다. 문장 자체는 새로 뽑으므로 "새 test 세트"이지만 틀은 v1 이 학습에서 본 적 없는 틀이다.
2. **제미나이 원본(`gemini_raw.jsonl`)은 고치지 않는다.** 수량 라벨 보정은 불러올 때 코드로 하고, 고친 행 목록을 별도 파일로 남긴다.
3. **되묻기 후보에 `other` 는 넣지 않는다.** top-2 중 하나가 `other` 이면 선택지 없이 "다시 말씀해 주세요". 그래서 정답이 `other` 인데 되묻기가 걸리면 "선택지에 정답이 있음"으로 세지 않는다(엄격 기준). 참고용으로 `other` 재요청을 성공으로 센 느슨한 기준도 같이 낸다.
4. **τ 는 val 의도분류 확률로 고른다 (test 는 보지 않음).** 후보 0.05~0.50 (0.05 간격). 되묻기 비율 ≤ 10% 인 것 중 되묻기 포함 성공률이 가장 높은 τ. 동률이면 작은 τ.
5. **SMOKE 실행은 별도 폴더(`out_smoke/`)에 쓴다.** out/ 의 정식 결과를 덮어쓰지 않기 위해 환경변수로 경로를 바꾼다.

## 2단계 선택지로 되묻기 (결과)
| 항목 | 값 |
|---|---|
| val tau 훑기 | results/v2/ask_sweep_val.csv (tau 0~0.5) |

### (중요) 지시된 tau 선택 규칙의 한계 — 실측으로 확인됨
val 훑기에서 **실행 정확도는 tau 가 커질수록 계속 올라가는데(0.916 → 0.944 at tau=0.5), 지시된 기준인 '되묻기 포함 성공률'(의도분류 기준)은 반대로 내려간다**(0.916 → 0.898).
그래서 이 기준은 구조적으로 **되묻기를 가장 적게 하는 tau** 를 고르게 되고, 실제로 tau=0.05 가 뽑혀 test 에서 431건 중 2건만 되묻는다. 즉 **이 기능은 거의 발동하지 않는다.**
- SMOKE 때 같은 현상을 보고 "전체 학습 후 재확인"이라고 적어 두었는데, 전체 학습 후에도 그대로 재현됐다.
- 지시받은 규칙을 바꾸지 않고 그대로 따랐고, 그 대가를 여기 적어 둔다. 실행 정확도를 기준으로 고르면 tau≈0.4~0.5 가 뽑히며 그때 되묻기 비율 4~6%, 실행 정확도 0.937~0.944 다 (results/v2/ask_sweep_val.csv 의 같은 표).
- 되묻기 자체의 동작(선택지 문장, "배송지/물건/첫 번째" 같은 답 이어받기)은 데모 셀에서 정상 확인됨.

### 원인 A — 1단계 라벨 수정의 예견된 부작용 (틀 `{item} 박스 하나 {issue}`, test 17건)
- 1단계 감사(노트북 11번 셀)에서 이 틀의 고정 문구 "박스 하나"에 수량 표현이 있는데 정답에 qty/unit 이 없던 것을 찾아 `LITERAL_QTY` 로 **qty=1, unit="박스"** 로 고쳤다. 이건 v2 test 숫자를 보기 전에 기록된 사실이다(1단계 표).
- 그런데 이 틀은 **v1 의 고정 틀 배정에서 test 로만 배정돼 있다**(train 0건 / test 17건). template_split_v1.json 만 봐도 알 수 있는 사실이다.
- 동시에 1단계에서 "둘·다섯"처럼 **단위 없이 말하면 정답에 qty 만** 쓰는 규칙(BARE_RATE)을 넣었다. "하나"도 그 목록에 있다.
- 결과: v2 는 학습에서 "박스 하나"를 한 번도 못 본 채 "하나 → 단위 없음" 규칙만 배워서 `{"qty":1}` 을 내보낸다(unit 누락). v1 은 이 틀에서 13/17 정답, v2 는 1/17.
- 즉 **1단계가 report_issue 의 라벨 버그를 없앤 대가가 학습 데이터에 없는 표현으로 옮겨 간 것**이다. 다음 반복에서는 `{qty}` 자리를 "박스 하나"처럼 단위-먼저 형태로도 렌더링해 train 에 넣어야 한다(틀 목록은 그대로 두므로 고정 배정도 유지됨).

### 원인 B — 설명되지 않는 일반화 손실 (틀 `물건 확인할게`, test 13건)
- v2 오답을 읽다가 발견한 관찰이다(사전에 예측한 것이 아님).
- 이 틀도 train 0건 / test 13건이고 정답은 `scan` 이다. v1 은 13/13 맞혔고 v2 는 0/13 으로 전부 `stop_items` 라고 답한다.
- 데이터상 train 의 `물건` 이라는 단어가 stop_items 쪽에 많아 그쪽으로 끌린 것으로 보이나, v1 도 같은 배정으로 학습했는데 맞혔으므로 **원인을 확정하지 못했다. 미해결로 남긴다.**

| PyTorch | 0.9072 | - | 259.8 MB | 15.1 ms |
| ONNX fp32 | 0.9072 | 1.000 | 259.9 MB | 6.5 ms |
| ONNX int8 | 0.9118 | 0.9907 | **65.3 MB** | **2.9 ms** |
- int8 이 정확도가 0.5%p 높게 나온 것은 431건 기준 2건 차이로, 양자화가 더 좋아진 게 아니라 측정 오차 범위다. 예측 일치율 99.07%(4건 불일치)로 보는 것이 맞다.
- 시간은 **이 PC 의 CPU** 값이며 보드(RK3588) 값이 아니다.
- 보드용 추론: export/intent_onnx/infer.py (onnxruntime + tokenizers 만 필요, torch 불필요). 실행 확인됨.

### 4-2 RKLLM W8A8 (변환 미실행)
- **미실행 이유: 이 PC 에 변환 도구가 없다.** rkllm-toolkit 은 x86 Linux 전용인데 WSL 배포판·Docker·toolkit 휠 모두 없다(환경 정보가 "모름"으로 비어 있었음).

  - 캘리브레이션 450건 저장 -> export/calibration_w8a8.json (RKLLM 형식: 채팅 템플릿 적용 프롬프트 + 정답)
